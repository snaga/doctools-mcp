# 2. インデックス構築プロセスの統合と効率化

日付: 2026-01-31

## ステータス

Accepted（承認済）

## コンテキスト（背景）

大量のドキュメントをインデックス化する際、以下の課題が顕在化していた。

*   **処理の停止**: 特定のファイルの変換処理が長時間化またはハングアップし、バッチ処理全体が停止してしまうことがある。
*   **非効率な更新**: 毎回すべてのファイルを再スキャン・再変換しており、ドキュメント量が増えるにつれて処理時間が肥大化している。
*   **不完全な同期**: インデックス作成後にファイルが削除された場合、インデックス内に古い情報が残り続け、検索結果に「存在しないファイル」が表示される問題がある。これを解消するには手動での削除操作が必要だった。
*   **エラー追跡の困難さ**: どのファイルの取り込みに失敗したのか、後から特定するのが難しい。

## 決定事項

これらの課題を解決するため、インデックス構築プロセス (`index_ctl`) を抜本的に見直し、以下の機能を実装することを決定した。

1.  **コマンドの統合と自動化**:
    *   従来の `build`（新規作成）と `update`（更新）を統合し、`build` コマンド一つで「存在すれば更新、なければ作成」を行うようにする。
    *   `build` コマンドの最後に、自動的にファイルシステムとの同期（削除済みファイルの除去）を実行する。

2.  **差分更新の導入**:
    *   Whoosh インデックスのスキーマに `mtime`（最終更新日時）フィールドを追加する。
    *   更新処理時、ファイルシステムの `mtime` とインデックス内の `mtime` を比較し、変更があったファイルのみを再処理することで、パフォーマンスを劇的に向上させる。

3.  **タイムアウト制御**:
    *   1ファイルあたりの処理にタイムアウト（デフォルト30秒）を設け、長時間化する処理を強制終了させることで、バッチ処理全体の停止を防ぐ。

4.  **エラーログの出力**:
    *   変換エラーやタイムアウトが発生したファイルの情報を、JSON形式のログファイルに出力し、事後確認を容易にする。

## 結果

### メリット
*   **運用性の向上**: 単一のコマンドを実行するだけで、インデックスを最新かつクリーンな状態に保てるようになる。
*   **堅牢性**: 不正なファイルによるプロセス停止を防ぎ、バッチ処理が最後まで完了することを保証できる。
*   **パフォーマンス**: 差分更新により、2回目以降のインデックス構築時間が大幅に短縮される。

### デメリット
*   **スキーマ変更**: 既存のインデックスとの互換性がなくなるため、本機能のリリース時にインデックスの再構築（フルビルド）が必要になる。
