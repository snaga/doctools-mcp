# ADR 0004: 標準エラーレスポンス形式の導入

## ステータス
承認済み

## コンテキスト
これまで、各 MCP ツールでエラー（例外）が発生した際のレスポンス形式が統一されていなかった。一部のツールは単にスタックトレースを返したり、`{"status": "error", "detail": "..."}` のような簡易的な形式を返したりしていた。

AI エージェント（Gemini-CLI 等）がツールを呼び出した際、エラーの内容（ファイルがないのか、権限がないのか、あるいは入力値が不正なのか）を正確に理解し、それに基づいた適切な自己修正（リトライやユーザーへの正確な報告）を行えるようにするためには、機械可読性の高い統一されたエラーフォーマットが必要である。

## 決定
全ての MCP ツールおよびサービス層において、エラー発生時に以下の JSON 構造を持つレスポンスを返却することを決定した。

```json
{
  "status": "error",
  "detail": "エラーの具体的な内容を示すメッセージ",
  "type": "例外クラス名（FileNotFoundError, ValueError 等）"
}
```

- **status**: 常に `"error"`。
- **detail**: 人間および AI が理解可能なエラーメッセージ。
- **type**: Python の例外クラス名。これにより AI はエラーの「性質」をプログラム的に判断できる。

この共通フォーマットを生成するために、`src/doctools/util_service.py` に `format_error_response(e: Exception)` 関数を実装し、全ツールの `except` ブロックでこれを使用する。

## 帰結
- **メリット**:
    - AI エージェントがエラーの性質を `type` フィールドで判別しやすくなり、より高度な自律的復旧や提案が可能になる。
    - サーバー全体の堅牢性が向上し、予期せぬクラッシュ（ツールが何も返さない状態）を防げる。
    - テストコードにおいて、エラーケースの検証（正しい例外が投げられているか）を厳密に行えるようになる。
- **デメリット**:
    - 既存のテストコード（古いエラー形式を期待していたもの）を全て更新する必要がある（本セッションで実施済み）。
